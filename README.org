* Overview

Donkey is an opinionated modal editing minor-mode for Emacs, that
leverages Emacs' own built-in functions wherever possible. There is no
overlay state — just a minor-mode keymap that toggles on and off.

It is meant to be an *addition* to Emacs rather than a replacement.
What it provides are improvements layered on top of what is already
there; your existing keys, packages and habits are meant to survive
intact. A modal editor cannot be entirely free of friction, so the few
native behaviors it does take are named in full below rather than left
to be discovered.

** Design Philosophy

- An addition to Emacs, not a replacement — improvements layered on
  top, never a reimplementation of what already works
- As little friction with native Emacs as possible; whatever cannot be
  kept is named in full rather than left to surprise you
- Leverage Emacs native commands and built-in functions wherever possible
- Custom commands only where beneficial
- No overlay-based state tracking — just minor-mode keymaps
- Graceful handling of optional dependencies (smartparens, org-mode)
- Cross-platform support (Linux/Wayland/X11, macOS, Windows)
- Terminal mode (=emacs -nw=) support with DECSCUSR cursor sequences

** What DONKEY takes from native Emacs

Concretely: your =C-x= and =C-c= prefixes, =M-x=, =C-h=, isearch, the
arrow keys, every =M-= binding and every package you have bound work
exactly as they always did, in both states.

What follows is the complete list of what does not — better named than
discovered.

*** Insert state

Exactly Emacs, with one key changed: =C-g= returns to Normal state
instead of running =keyboard-quit=. It still deactivates the mark, and
in the minibuffer or an excluded mode it hands off to the real
=keyboard-quit=, so the escape hatch is intact where you need it.

It also stops a keyboard macro that is being recorded, the way
=keyboard-quit= does. The one thing it still does not do is signal a
=quit= condition. Everything else you reach for =C-g= for is untouched —
interrupting a running command is handled below the keymap, isearch has
its own, and =C-x C-g= is a different key sequence.

If smartparens is loaded, whatever key runs =sp-cancel= also returns to
Normal state.

*** Normal state

| What                    | Native Emacs                    | In DONKEY               |
|-------------------------+---------------------------------+-------------------------|
| Printable characters    | insert themselves               | run commands            |
| Digits =0=–=9=          | insert themselves               | unbound; use =C-u N=    |
| =RET=                   | =newline=                       | nothing, in an editing buffer |
| =BACKSPACE= / =DELETE=  | delete a character              | nothing                 |

(=BACKSPACE= and =DELETE= are blocked under all four of the key names
they arrive as — =<backspace>= and =<delete>= on a graphical frame,
=DEL= and =<deletechar>= in a terminal — so the block behaves the same
whichever way you run Emacs.)

The first is the whole point of a modal editor rather than a cost. The
others are worth knowing:

- *No bare counts.* =3 j= is not "down three lines" the way it is in
  vi — digits are not prefix arguments here. =C-u 3 j= is, and every
  counted command takes it.
- *=RET= does nothing* in a buffer you are editing, on purpose:
  inserting a newline in Normal state is rarely what was meant. In
  =dired=, =magit=, =org-agenda= and other non-editing modes it is
  *not* inert — it hands the key back to whatever that mode had bound,
  so =RET= still opens the file, visits the entry, follows the link.
- *Backspace and Delete do nothing*, so a stray press cannot damage the
  buffer from Normal state. Use =d= or =x=.

Everything else falls through: =C-a=, =C-e=, =C-k=, =C-w=, =M-w=,
=C-y=, =C-s=, =C-SPC=, =C-/=, =M-f=, =M-b=, =M-^=, =C-x= …, =C-c= …,
=M-x=, =C-h= …, =TAB=, =C-u=, arrows, Home/End, PageUp/PageDown.

*** In dired, magit and other special buffers

DONKEY is on there too, and its single-letter commands take precedence
over the major mode's. A major-mode key that DONKEY does *not* bind
still works — suppressing self-insertion is done by remapping
=self-insert-command= rather than by claiming each letter, so anything
the mode bound to a real command survives. In =dired=, for example,
=n=, =t=, =q=, =^= and =+= all still do what dired means by them, while
=p=, =m=, =u=, =d=, =x=, =g=, =v=, =o=, =i=, =l= and =w= are DONKEY's.

Modes where suppressing keys would break the underlying process —
=eshell=, =term=, =vterm=, =comint= — stay in Insert passthrough
entirely. See Excluded Modes.

* Installation

Donkey isn't on MELPA, so pick whichever of these fits your setup.
All are equivalent; they just differ in how =donkey.el= gets onto
disk and onto your =load-path=.

** Manual

Place =donkey.el= at =donkey/donkey.el= inside your
=user-emacs-directory= (run =C-h v user-emacs-directory= to see
where that is on your system — typically =~/.config/emacs/= or
=~/.emacs.d/= on Linux and macOS, or the equivalent under =%APPDATA%=
on Windows), then add the following to your =init.el= or =config.el=:

#+begin_src emacs-lisp

  (let ((donkey-path (expand-file-name "donkey/donkey.el"
                                     user-emacs-directory)))
    (if (file-exists-p donkey-path)
        (load donkey-path nil t)
      (message "WARNING: Donkey modal module not found at %s." donkey-path)))

  (donkey-mode 1)

#+end_src

** use-package with a manual clone

Clone the repository into =donkey/= inside your
=user-emacs-directory=, then point =use-package= at it with
=:load-path=. A relative path is resolved against
=user-emacs-directory= automatically:

#+begin_src emacs-lisp

  (use-package donkey
    :load-path "donkey"
    :config
    (donkey-mode 1))

#+end_src

** use-package with =straight.el=

#+begin_src emacs-lisp

  (use-package donkey
    :straight (:host github :repo "yardquit/donkey")
    :config
    (donkey-mode 1))

#+end_src

** use-package with =quelpa=

The =:quelpa= keyword isn't built into =use-package= itself — it's
added by the separate =quelpa-use-package= package, so both =quelpa=
and =quelpa-use-package= need to be installed first:

#+begin_src emacs-lisp

  (use-package donkey
    :quelpa (donkey :fetcher github :repo "yardquit/donkey")
    :config
    (donkey-mode 1))

#+end_src

* Usage

Once =(donkey-mode 1)= has run (see Installation above), every buffer
starts in DONKEY Normal state, with one exception: buffers whose major
mode is on the Excluded Modes list (see below) — things like =eshell=
or a shell/terminal buffer — stay in ordinary Insert passthrough
instead, since suppressing keys there would break the underlying
process interaction.

- Press =C-g= to enter Normal state from any ordinary buffer. Excluded
  Modes are the exception, and the only one: there =C-g= does what it
  does in stock Emacs, and Normal state cannot be reached at all.
- In Normal state: =h=/=j=/=k=/=l= navigate; =i=/=I=/=a=/=A=/=o=/=O=/=c=
  enter Insert state at various positions (see Default Keybindings
  below for the full reference).
- In Insert state: standard Emacs behavior — nothing is remapped.
  Press =C-g= to return to Normal.
- The modeline shows the current state: =DONKEY[N]= (Normal),
  =DONKEY[I]= (Insert), or =DONKEY[E]= in an *excluded* mode. =E= is
  still Insert state — keys really do pass straight through — but it is
  reported separately because Normal state is unreachable there, so
  pressing =C-g= and seeing nothing change is the design rather than a
  stuck key.
- New to DONKEY? Press =g ?= (or =M-x donkey-tutor=) — see Tutor below.

** Navigation

|-----+-----------------+-------------|
| =h= | =backward-char= | Move left   |
| =j= | =next-line=     | Move down   |
| =k= | =previous-line= | Move up     |

** Visual Line Movement

| Key | Command                     | Description                           |
|-----+-----------------------------+---------------------------------------|
| =J= | =donkey-visual-next-line=     | Move down, extending visual selection |
| =K= | =donkey-visual-previous-line= | Move up, extending visual selection   |
| =V= | =donkey-visual-line-toggle=   | Toggle visual line selection          |
| =v= | =donkey-set-mark=           | Drop a mark and start selecting; =C-g= lets go |
| =M= | =donkey-mark-run-toggle=    | Toggle mark run mode: bare =w W b B s S= mark and grow |
| =(= =[= ={= ="= ='= =`= | =donkey-wrap-region= | Wrap active region with delimiter, see below |

=V=, =M= and =m v= toggle: pressing any of them a second time cancels
the selection it started (=M='s cancel press is the one *inside* its
mode; over an existing selection it adopts instead — see the mark run
section). =v= does not. It is =set-mark-command=, so a
second press drops a fresh mark where point is standing and begins
selecting again from there — the old selection is gone, but you are
still selecting. Use =C-g= to let go of a =v= selection.

*** Changing your mind

You can go from any of the four to any other without letting go first.
What becomes of the selection you already had is the whole of what
there is to know:

| Press | What happens to what was selected |
|-------+-----------------------------------|
| =M=   | *Adopted.* It becomes the run's starting selection, and the object keys grow it from there. |
| =m v= | *Reinterpreted.* The region's corners become the block. |
| =V=   | *Dropped.* A fresh session anchors on the line the cursor is on. |
| =v=   | *Dropped.* A new selection starts, empty, where the cursor stands. |

So =v l l l= on the =b= of "beta" selects =bet=, and =M w= then grows
it to =beta= — the run picked up what was there rather than starting
over. =m w M w= extends the marked word the same way.

Three exceptions:

- Inside a mark run, =v= and =V= are *refused*. Neither can take a
  run's selection over honestly, and both used to drop it without
  saying so. Leave first with =M=, =C-g=, or any action key.
- A *rectangle* is the one selection =M= will not adopt — a block has
  no forward end for the object keys to own — so =M= drops it and
  starts a fresh run on the word under the cursor.
- Reaching =m v= *from* =V= gives a full-width block. =V= selects whole
  lines, so the corners =m v= inherits are the whole line's width.
  Start =m v= from nothing, or from a =v= selection, for a narrow one.

The =m= keys end nothing: =m w= inside a run grows the run, and outside
one it marks and leaves you selecting. Over a rectangle it clears the
block first, no mark command being able to act on columns. =%= is the
same — inside a run it takes the whole buffer and the run carries on.

All four selections keep an echo-area reminder up for as long as they
are live, and it goes when they do:

| =v=   | =Linear selection: any motion extends, v re-anchors, C-g to cancel= |
| =V=   | =Visual line: J/K whole lines, j/k by char, V to cancel= |
| =m v= | =Rectangle: any motion sizes the block, m v or C-g to cancel= |
| =M=   | =Mark run: w/b words, W/B symbols, s/S sentences, m p/m P paragraphs, * other end, M to cancel= |

Only one of them is ever on screen: a selection entered over another —
=M= adopting a =v= region, =m v= reinterpreting one — hands the echo
area to the mode that took over. A command that prints a message of
its own keeps its echo, and the next motion brings the reminder back.

The =v= and =m v= lines say what the other two do not have to. Those
own their keys and can list them; these own none — every motion
extends a =v= selection or sizes a rectangle — so what is worth saying
is how to let go, which is the part neither key tells you.

Within a visual-line session (started with =V=), =J= and =K= extend the
selection by whole lines, always anchored to the line =V= was pressed
on. Plain =j= and =k= still work too, extending character-wise from
wherever point currently is -- so a selection can stop mid-line. The
two can be mixed freely: after moving with =j=/=k=, pressing =J=/=K=
snaps the selection back to whole lines from the original anchor.

=J= and =K= take a count like =j= and =k= do, so =C-u 3 J= is the same
as pressing =J= three times, and a negative count moves the other way.

The echo-area reminder =V= shows stays visible across the session's
motions, as mark run mode's does; a command that prints its own
message keeps its echo, and the next motion brings the reminder back.

If the buffer is narrowed so that the anchor line is no longer visible,
=J= and =K= stop extending and just move by lines — the session cannot
honestly continue from an anchor the buffer is not showing. Widening
brings it back.

=y= and =d= act on *whole lines* during a visual-line session, including
the newline that ends the last one. So =V d= removes the line outright
rather than emptying it and leaving a blank behind, and =V J y= gives a
kill that =p= inserts as complete lines instead of splicing onto whatever
line it lands in. This matches what banking (=m l=) has always done. A
character-wise region made with =v= is unaffected — it still means
exactly the characters it covers.

The highlight does not show that trailing newline: it stops at the end
of the last line, so a =V= selection always looks one character shorter
than what =y= and =d= actually take. That is deliberate — the
highlight ends where the text does, and =J=/=K= count lines from where
point sits — and only the two commands widen. Worth knowing before
reporting it: the newline goes along even though nothing marks it.

** Insert Mode Entry

| Key | Command                         | Description                         |
|-----+---------------------------------+-------------------------------------|
| =i= | =donkey-insert-here=              | Insert at current position          |
| =a= | =donkey-insert-after=             | Insert after current char           |
| =I= | =donkey-insert-beginning-of-line= | Insert at beginning of line         |
| =A= | =donkey-insert-end-of-line=       | Insert at end of line               |
| =o= | =donkey-open-below=               | Open new line below, enter Insert   |
| =O= | =donkey-open-above=               | Open new line above, enter Insert   |
| =c= | =donkey-change=                   | Change char or region, enter Insert |

During a visual-line session (=V=), =c= does *not* take the trailing
newline the way =y= and =d= do. =V c= empties the line and leaves point
on it ready to type, rather than removing the line and dropping you onto
the next one — this is vi's =cc=, the linewise change that keeps its
line. =V J c= collapses the whole span to a single empty line. It is the
one place the two line commands part company: =V d= takes the newline
because you asked for the line to go, =V c= keeps it because you asked
to replace what is on it.

Under =rectangle-mark-mode= (=m v=), =c= behaves differently: it runs
=string-rectangle=, which prompts for the replacement text and applies
it to every covered line itself. Since that finishes the whole edit,
DONKEY stays in *Normal* state afterward rather than entering Insert —
there is nothing left to type, and dropping into Insert would make the
next navigation keypress self-insert.

** Editing

| Key   | Command                      | Description                      |
|-------+------------------------------+----------------------------------|
| =d=   | =donkey-delete=                | Delete char or region (Helix)    |
| =x=   | =donkey-delete=                | Delete char or region (Vim)      |
| =D=   | =kill-line=                  | Kill to end of line              |
| =C=   | =donkey-comment-dwim=          | Comment/uncomment line or region |
| =g j= | =donkey-join-line=             | Pull the following line up       |
| =>=   | =donkey-indent-region-or-line= | Indent region or line            |

=g j= absorbs the line *below* the one you are on, the direction vi's
=J= and Helix's =J= both use. =C-u 3 g j= collapses three lines into
this one. Emacs' own =M-^= goes the other way — pulling the current
line up onto the previous one — and is untouched, since every =M-= key
falls through in Normal state.

On the last line there is nothing below to pull up, so nothing happens
and it says so. Left to =join-line= this quietly removed the buffer's
final newline instead — the "line" below the last one is the empty
position after it — with no visible change to show for it until a diff
reported =\\ No newline at end of file=. A count that overshoots stops
there too.

This moved off =C-j=, and changed direction with it. =C-j= looks free
but is not: globally it is =electric-newline-and-maybe-indent=,
and in =*scratch*= or any =lisp-interaction-mode= buffer it is
=eval-print-last-sexp=. A minor-mode keymap outranks the major mode, so
binding it here quietly cost the scratch buffer its evaluate-and-print
key. The old binding also ran =join-line= with no argument, which joins
with the *previous* line — the opposite of what this table had always
described.

** Yank and Paste

| Key | Command          | Description                                 |
|-----+------------------+---------------------------------------------|
| =p= | =donkey-yank=      | Yank from clipboard, replacing region or banked lines |
| =P= | =donkey-yank-rectangle= | Paste =killed-rectangle= as a block of columns |
| =y= | =donkey-copy=      | Copy region (or char at point) to kill ring |

=C-u 3 p= pastes three copies — the vi reading of a count on a paste,
not the Emacs one. Emacs takes a prefix argument on =C-y= to mean *which*
kill-ring entry to pull, but nothing is given up here: =C-y= is untouched
in Insert state, so that meaning is still available on the key it belongs
to. A count below 1 pastes nothing, matching zero and negative counts
elsewhere.

On a *rectangle*, a count widens the block rather than stacking copies:
=C-u 2 P= repeats each row's text, so a three-row block comes back twice
as wide. That is what a count on a blockwise paste does in vi, and it is
the only reading that makes sense — pasting the block twice in sequence
would drop the second copy partway down and across the first.

Stepping back through earlier copies is Emacs' own =M-y= (=yank-pop=),
which DONKEY does not rebind — it works in both states, on the key it
has always been on.

=p= replaces whatever is selected — an active region, banked lines, or
both together — exactly as =y= and =d= act on them, and spends the bank
the same way. Pasting over banked lines drops the paste where the first
banked line was:

#+begin_example
  AAA one     <- banked          ZZZ
  BBB two                 =p=    BBB two
  CCC three   <- banked   ==>    DDD four
  DDD four                       EEE five
  EEE five
#+end_example

With *nothing to paste* — an empty kill ring and no clipboard content —
=p= does nothing at all and says =Nothing to paste=. It does not remove
the selection first: the replaced text is deleted rather than killed, so
losing it to a paste that then had nothing to insert would have put it
out of reach of everything but =undo=.

** Mark Objects (=m= prefix)

| Key   | Command                    | Description                          |
|-------+----------------------------+--------------------------------------|
| =m w= | =donkey-mark-word=           | Mark word at point                   |
| =m W= | =donkey-mark-symbol=         | Mark symbol (hyphens, underscores)   |
| =m b= | =donkey-mark-word-backward=  | Mark word, or grow a selection backward |
| =m B= | =donkey-mark-symbol-backward= | Mark symbol, or grow a selection backward |
| =m s= | =donkey-mark-sentence=       | Mark sentence                        |
| =m S= | =donkey-mark-sentence-backward= | Mark sentence, or grow a selection backward |
| =m p= | =donkey-mark-paragraph=      | Mark paragraph                       |
| =m P= | =donkey-mark-paragraph-backward= | Mark paragraph, or grow a selection backward |
| =m i= | =donkey-mark-inner=          | Mark inside delimiter pair           |
| =m a= | =donkey-mark-outer=          | Mark including delimiter pair        |
| =m I= | =donkey-mark-sexp-inner=     | Mark inside balanced expression      |
| =m A= | =donkey-mark-sexp-outer=     | Mark including balanced expression   |
| =m v= | =donkey-rectangle-mark-mode= | Toggle rectangle mark mode           |
| =m l=   | =donkey-bank-selection=      | Bank lines, keep navigating          |
| =m u=   | =donkey-unbank-line=         | Unbank the line at point             |
| =m U=   | =donkey-unbank-section=      | Unbank the whole run at point        |
| =m DEL= | =donkey-clear-banked-selection= | Discard all banked lines (Backspace or Delete) |

=m w= marks a word; =m W= marks a symbol, which is the same thing plus
whatever the major mode counts as holding a name together. Hyphens and
underscores usually do, so =m W= anywhere in =send-mail_to= takes all of
it while =m w= takes only =send=, =mail= or =to=.

Periods and commas are the mode's call too, and modes disagree: in
=emacs-lisp-mode= =m W= on =foo.bar= takes the whole of it, while in
=python-mode= and =text-mode= it stops at =foo=. One part is DONKEY's
own rather than the mode's — a trailing =.= or =,= is always dropped, so
=m W= on the last name of a sentence gives you the name without its full
stop even where the mode would have included it.

=m w=, =m W=, =m s= and =m p= all report =No ... at or before point=
rather than marking nothing when there is nothing of substance to mark —
an empty buffer, or one holding only blank lines and whitespace. A blank
line *between* paragraphs is not such a case: =m p= marks the paragraph
above it, as it always has.

=donkey-mark-inner=/=donkey-mark-outer= support =( [ { < " ' ` ‘ ’ “ ” = * ~ | \ / : + _ $=
by default -- an alist of (OPEN . CLOSE) pairs in =donkey-mark-pair-delimiters=
(a Customization Group variable). For symmetric delimiters (e.g. straight
or curly single quotes, where the same character both opens and closes a
pair), OPEN and CLOSE are identical. Matching is always case-sensitive,
regardless of the buffer's own =case-fold-search= setting. Add or remove
entries in your =config.el= to change what's recognized, e.g. to add
=#= as a language's inline-comment marker and remove =~= (freeing that
key up for something else):

#+begin_src emacs-lisp

  ;; Add a pair
  (add-to-list 'donkey-mark-pair-delimiters '(?# . ?#))

  ;; Remove a pair
  (setq donkey-mark-pair-delimiters
        (assq-delete-all ?~ donkey-mark-pair-delimiters))

#+end_src

For asymmetric pairs (e.g. =(= and =)=), nested occurrences of the same
pair are matched correctly -- the outer =(= of =(a(b)c)= selects
=a(b)c=, not just up to the first =)= found. This is a plain character
scan, though, not syntax-table aware: unlike =donkey-mark-sexp-inner=/
=donkey-mark-sexp-outer=, it doesn't know about strings or comments, so
the same character appearing inside one can still throw off the match.
For balanced expressions in real code, use =donkey-mark-sexp-inner=/
=donkey-mark-sexp-outer= instead -- those are always syntax-aware and
need no delimiter list.

With no matching pair either way, both commands signal an error and
leave point exactly where it was, instead of landing somewhere else in
the buffer as a side effect of the failed search.

** Banking Lines (Non-Contiguous Selection)

Emacs has a single region, so you normally can't select line 3, skip a
few, and add line 9 to the same selection. =m l= works around that:
it *banks* the lines you have selected right now, highlights them with
the =donkey-banked-selection= face, and releases the mark so you can
carry on navigating and selecting freely.

Repeat as often as you like, then press =y= or =d= — both act on every
banked line at once:

#+begin_example

  V J          select lines 0-1
  m l          bank them, mark released
  j j j        navigate past lines you want to skip
  V J          select lines 4-5
  m l          bank those too
  j j j        navigate on
  V            select line 8
  y            copies lines 0,1,4,5,8 as one kill

#+end_example

The live region counts too, so the final piece never has to be banked
explicitly — in the example above, line 8 is included by =y= without a
third =m l=.

=y=, =d= and =p= all act on the banked lines plus the live region, and
all three spend the bank once they have — only the spans they actually
acted on, so banks hidden by narrowing survive to count again once the
buffer is widened.

=c= is the exception: it changes the character at point and leaves banks
standing. Nothing has been settled about what changing a multi-line bank
should mean, so it does not guess.

*** Banks and rectangles

A rectangle is columns and a bank is whole lines, so no command can act
on both. One rule settles it everywhere: *the live selection you are
looking at wins, and the bank is the fallback.*

| Situation                              | What acts                  |
|----------------------------------------+----------------------------|
| =y= / =d= with a rectangle drawn       | the rectangle; banks survive |
| =y= / =d= with no rectangle drawn      | the banks                  |
| =p= with lines banked                  | the banks                  |

The reasoning is that a drawn rectangle is on screen and the bank is
the fallback, so whichever one you can currently see is the better guess
at what you meant. Nothing is discarded either way — take the rectangle
and your banks are still waiting afterwards.

Pasting needs no such rule. =p= reads the kill ring and system
clipboard; =P= reads =killed-rectangle=. They are separate stores and
each key names one of them, so nothing has to be inferred.

This used to be one key. =p= decided by tracking which store had been
written more recently, in a flag, because Emacs gives a rectangle no way
to say so itself — the kill ring is untyped text and =killed-rectangle=
is a separate variable that is only ever written, never cleared. The
flag went stale in ways a reader could not predict: importing the system
clipboard during a paste counts as a kill in Emacs, so a paste could
retire the pending rectangle in a graphical session and not in a
terminal one. Two keys need no bookkeeping and behave identically
everywhere.

The three commands used to disagree, each silently: =y= and =d= took
the banks and ignored a rectangle you were looking at, while =p= took a
rectangle out of =killed-rectangle= and ignored banks highlighted on
screen. Drawing a rectangle over two rows and pressing =d= deleted
three whole lines.

Note =m l= collapses the two states in the other direction: banking
while a rectangle is drawn banks the whole lines it covers and ends
rectangle mode.

One consequence worth knowing: when a bank claims =p=, the kill ring
may hold something *older* than the rectangle, since a rectangle copy
never touches the kill ring. That is the entry =p= pastes; the
rectangle is reached with =P=, which the bank never claims.

=m l= toggles, with or without a region:

- *No region* — banks the current line; pressing it again on an
  already-banked line *unbanks* that line.
- *Region over an already-banked block* — unbanks the whole block in
  one press, leaving every other bank untouched. This is how to take
  back a multi-line bank without walking it line by line or clearing
  everything.
- *Region over a partly-banked block* — banks the rest of it. A block
  only toggles off once it is uniformly on, so press again to then
  clear it.

*** Taking banks back

Banked lines are consumed by =y=, =d= or =p=. To remove them without
doing anything else, there are three levels:

| Key     | Removes                                          |
|---------+--------------------------------------------------|
| =m u=   | the banked line at point                         |
| =m U=   | the whole contiguous run point is standing on    |
| =m DEL= | every bank in the buffer                         |

=m u= and =m U= only ever *remove*. Pressing either on a line that is
not banked reports =No banked line at point= / =No banked section at
point= and changes nothing, so you can lean on them without tracking
the state of each line.

A "run" is every banked line adjacent to the one you are on — exactly
the stretch that =y= and =d= treat as one piece — so a block you banked
line by line comes back off in one press of =m U=, without re-selecting
it. Banks outside the run are left alone.

=m DEL= is =m= followed by *Backspace*, which is what Emacs calls
=DEL=. The physical *Delete* key is bound to the same command, so
whichever of the two you reach for clears the bank.

Notes:

- Banking is whole-line only. Partial selections are rounded out to the
  full lines they touch.
- Adjacent banked lines are copied and deleted as one contiguous run,
  so banking a block line-by-line gives the same result as selecting it
  in one go.
- =d= deletes back-to-front internally, so the lines you banked are the
  lines that get removed regardless of how the earlier deletions shift
  positions.
- Banked lines follow the text as you edit around them. If a banked
  line is deleted outright, its bank goes with it rather than lingering
  as an invisible, empty selection.
- Turning off =donkey-mode= discards any banked lines along with the
  rest of DONKEY's state.

*** Counts

A count works wherever "how many" means something, and it always means
exactly that — so =C-u 3 x= deletes three characters and =C-u 2 m s=
marks two sentences. Every motion takes one, as does every =m= key that
selects a thing, along with =d=, =y=, =c= and =p=. The keys with no "how
many" in them — entering INSERT, toggling a state, asking for help —
ignore a count rather than refusing it.

| Keys        | Effect                                  |
|-------------+-----------------------------------------|
| =C-u 3 p=   | paste three copies                      |
| =C-u 2 P=   | paste the rectangle twice as wide       |
| =C-u 3 J=   | down three lines, extending a visual selection |
| =C-u 3 K=   | up three lines, extending a visual selection |
| =C-u 3 x=   | delete three characters                 |
| =C-u 3 y=   | copy three characters                   |
| =C-u 3 c=   | change three characters                 |
| =C-u 3 m w= | mark three words                        |
| =C-u 3 m b= | mark the word and the two before it     |
| =C-u 2 m W= | mark two symbols                        |
| =C-u 2 m s= | mark two sentences                      |
| =C-u 2 m p= | mark two paragraphs                     |
| =C-u 2 m A= | mark two levels out of the expression   |
| =C-u 2 m i= | mark two levels out of the delimiter pair |
| =C-u 3 S=   | jump back three recorded positions       |
| =C-u 3 m l= | bank three lines                         |

A count larger than the text remaining does what it can and stops, rather
than erroring — =C-u 99 x= at the end of a buffer clears the rest.

Bare digits are not counts: =3= is not bound, because =suppress-keymap=
is called with digits left out so they cannot self-insert. Use =C-u=.

**** Zero and negative counts

A *negative* count works backwards from point, the same way it does for
stock =C-d=: =C-u -2 x= deletes the two characters *before* point, and
=C-u -2 m w= marks the two words before the one the cursor is on. As
with a positive count, running out of buffer stops at the edge and
reports instead of erroring.

A count of *zero* does nothing at all — =C-u 0 x= deletes no characters,
=C-u 0 y= leaves the kill ring untouched rather than pushing an empty
string over whatever =p= was about to paste. =C-u 0 c= is the one
exception worth naming: it changes no text but still drops into INSERT
state, because entering INSERT is what the command is for and only the
deletion is governed by the count.

=m s= is one exception: a count below 1 is treated as 1. That command is
defined in terms of the sentence *ahead* of the cursor — it normalizes
forward and reports =No sentence after point= for anything ending behind
where it started — so zero and negative counts have nothing they could
mean but that error.

=m b=, =m B=, =m S= and =m P= are the others, treating a count below 1
as 1 for the mirrored reason: they *are* the backward direction, so a
negative count has nothing left to point at that =C-u -2 m w= and
friends do not already say.

**** Repeating a mark key extends the selection

Pressing =m w=, =m W=, =m s= or =m p= a second time straight away
*grows* the selection by another word, symbol, sentence or paragraph
instead of re-marking the same one, and keeps growing on each further
press until the buffer runs out. So =m s m s m s= is another way to say
=C-u 3 m s=, and the same holds for the other three.

All four grow *backward* as well: =m b= adds the word before the
selection, =m B= the symbol, =m S= the sentence, =m P= the paragraph,
and either direction continues the same run. Starting on =that= in
"This buffer is for text that is not saved", =m w m w m b= selects
=text that is= — two words forward, one back. Pressed fresh, with no
run to continue, each backward key selects exactly what its forward
partner would; the two differ only in the direction further presses grow.

Runs mix objects freely: each press adds one object of its own kind at
its own end, so =m w m s= grows the word selection forward to the end
of its sentence, and =m s m b= takes the sentence plus the word before
it. A backward press whose end sits inside a larger object of its own
kind first reaches that object's start — =m B= after marking the word
=two= inside =b-two= completes the symbol backward — and the next
press adds a whole one.

=M= is the =m= prefix held down for you: it enters *mark run mode*,
where the bare letters =w W b B s S= run exactly what their
=m=-prefixed keys run, so =M w w b= selects what =m w m w m b=
selects. The first letter marks afresh, later letters grow the one
selection, counts work (=M C-u 3 w=), and objects mix as above.

The echo-area reminder stays visible for as long as the mode is
active, and goes when the mode does. It names the keys whose *subject*
the mode changes and no others: =w= moves by a word in normal state
and marks one here, which nobody could guess from the key. A key that
keeps its subject is left out — =h j k l= still move, =J= and =K=
still work on lines, =u= and =U= still step back and forward, of the
run rather than the buffer. Spelling those out spent the line on the
keys least in need of it, and the line has to be taken in at a glance.
The complete list is here and in the tutor.

=M= arrives holding the word under the cursor, since that is what
nearly every run starts from — pressed on =that=, the word is
selected before you have touched a letter, so =M d= takes it and =M w=
is the word the prefix would have marked. Only a word actually under
the cursor: on whitespace, or a blank line, the mode arrives empty
rather than reaching back for the word above. The head start is not
the run's first press, so nothing about the letters changes — =M w w b=
is still =m w m w m b=.

The =m= prefix still works inside the mode and needs no thinking
about: =m w= runs the very command the bare =w= runs, so the mode
survives it and the run keeps growing — =M w m w w= selects three
words, and the two spellings can be mixed mid-run. Paragraphs are
reached that way and only that way: =p= and =P= stay the *paste* keys
inside the mode, so =M w p= replaces the marked word with the kill
ring, and =m p= / =m P= grow the run by paragraphs. Lettering them
cost the mode the one ordinary edit it could not otherwise make — =d=,
=y=, =x= and =c= all act on a mark run selection, and only pasting had
nowhere to go.

=h j k l= move point without ending the run, adjusting the selection's
near end the way =j=/=k= adjust a =V= session. =g h= and =g l= reach
the line's ends, and unlike =h j k l= they own an end apiece rather
than both moving point, so they add up: =M w g h g l= selects the
whole line's text, in either order. =g g= and =g e= (and =G=) do the
same for the buffer's ends, so =M w g g g e= is everything from a word
in the middle. With nothing selected yet all four are still plain
motions, for placing the cursor before marking. Other =g= keys are not
shadowed and end the mode like any foreign key.

=J= and =K= make lines a growable object of the mode: fresh, either
marks the current line, and further presses grow by whole lines — =J=
at the bottom end, =K= at the top, a mark mid-line completing its own
line first. Whole lines means the newline too, so =M J d= removes the
line outright rather than leaving the blank one behind, and =M J y=
yanks back as a line. The highlight reaches the next line's first
column to show it.

=u= puts the run back where the last press found it and =U= puts it
forward again, one press per step, the motions and =*= included. A run
only ever grows — =b= after =w= adds a word at the other end rather
than taking one back — so without them a press that reached further
than it looked left cancelling and starting again as the only way out.
A press that is neither of the two ends the redo, a new branch having
nothing to redo onto, and each reports rather than guessing when there
is nothing left.

The pair is why =U= is bound at all. Outside the mode =u= and =U= are
=undo= and =undo-redo=; =u= was taken for the run while =U= still
meant the buffer, so the press anyone would reach for after =u= redid
a *text edit*, dropped the selection and lapsed the mode without
saying so — worst exactly where it was likeliest, straight after =u=.
Inside a run both keys are about the run, which is the same idea one
level down. Outside it they are untouched.

=*= swaps point and mark, so the motions adjust the selection's
*other* end — vi's =o= in visual mode. The object keys own fixed ends
and simply trade back before they grow, so =M w * w= selects what
=M w w= selects; the same goes for a motion that has walked point past
the mark, and for a selection a negative count left inside out.

Pressed with a selection already active — a =V= session, a =v= region,
or one the =m=-prefixed keys built — =M= *adopts* it into the mode
rather than dropping it: =m w M w= extends the marked word, and a
=V J= selection keeps its lines while the object keys grow it — whole
lines, the final newline included, so =V J M d= removes both lines
outright the way =V J d= does. A rectangle is the one selection =M=
drops rather than adopts, having no forward end for the family to own
— and having dropped it, =M= starts a run as it would over nothing at
all, so the press still leaves you somewhere to press a letter. An
*empty* selection is dropped the same way, so after a bare =v=
mid-word, =M w= still marks the whole word.

Any other key ends the mode and then does its ordinary job in the same
press — =M w w d= selects two words and deletes them. Two are held
back. A key that does nothing — one that is unbound, or =DEL= — leaves
the run standing, so a mistyped key costs a beep rather than the
selection. A mistyped *sequence* counts as one too: =m x= for =m w=,
or a slip after =g=, beeps and leaves the run exactly as it was. And =v= and =V= are refused: neither a fresh mark nor a
visual line session can own a mark run's selection, and both presses
used to drop the run and start over without saying so, which is worse
than being told to leave the mode first. =M= pressed again, inside the mode, drops the selection
and the mode, and =C-g= does the same, as it does for every selection.

=%= is a third exception, and the widest one: it marks the whole
buffer, so the mode keeps the selection and =u= takes it back, rather
than changing it on the way out. Nothing can grow a selection that
already covers everything, so the press after it simply finds nothing
to do.

Only these eight keys are in the family:
=m i= and =m a= count levels rather than objects, and a selection
started with =v= is still never grown by a mark key. All eight grow a
run inside =M= too; six of them have a bare letter there, and the
paragraph pair keeps its =m= prefix.

Any other key in between ends the run — =m w l m w= marks a single word
again rather than two. An active selection made some other way is left
alone: =v=, a few motions, then =m w= still marks the word at the
cursor. Emacs' own rule is wider than this and would extend that
selection too; DONKEY uses the narrower one so =v= keeps working the way
it reads.

=m i= and =m a= are not in this: they count *levels*, and one more level
out is not one more of the same thing. Use a count for those.

=m i= and =m a= take a count for *every* pair in
=donkey-mark-pair-delimiters=, but the two kinds count different things.
A nesting pair — =()=, =[]=, ={}=, =<>= — counts *levels*, resolving the
correctly balanced match at each one. A symmetric delimiter — a quote,
=*=, =~=, =/=, =_= — opens and closes with the same character, so there
are no levels to count and it counts *occurrences* outward instead:

#+begin_example
  "No use "writing on paper." That"
                ^ cursor here
#+end_example

- =m i "= → =writing on paper.=
- =C-u 2 m i "= → =No use "writing on paper." That=

That is a nearest-occurrence-each-way rule, not real nesting, and it can
be fooled — with the cursor between two *separate* quoted strings, =m i "=
already selects the gap between them rather than a quoted string, because
nothing in the text says which quote opens. A count inherits that; it
does not add a new way to go wrong.

*Give the count as =C-u 2= or =M-2=, not =C-2=.* Whether =C-<digit>=
reaches Emacs at all depends on the terminal — many do not transmit it
as a distinct key, and it is not worth relying on. =C-u 2= is a plain
control character followed by a digit and always gets through.

Watch out for bare =C-u=: on its own it means *four*, not one. =C-u m i=
asks for four levels of nesting, so on text only two deep it reports
=No enclosing '(' beyond that level= — the count overshot, the delimiter
is fine.

If a count seems to be ignored, =C-h k= followed by the keys you press
names the command Emacs actually received, which settles where it is
being lost.

Some commands are reachable by more than one key on purpose, so that
whichever editor you arrive from, the key you already know works:

| Key   | Does                | Familiar from |
|-------+---------------------+---------------|
| =g e= | end of buffer       | Helix         |
| =G=   | end of buffer       | Vim           |
| =d=   | delete char/region  | Helix         |
| =x=   | delete char/region  | Vim           |

=g g= needs no twin: both editors already use it for the start of the
buffer.

The duplication is deliberate and worth keeping — it is not a leftover.

One difference from Vim worth knowing: =d= here is *not* an
operator-pending key. It acts immediately on the selection, or on the
character at point when there is none, the way Helix's =d= does — so
=d d= deletes two characters rather than a line, and =d w= deletes a
character and then moves a word. To delete to the end of a line, use
=D=; to delete whole lines, select them first (=V=, =J=/=K=) and press
=d=.

* Excluded Modes

DONKEY Normal state is permanently disabled in certain major modes where
key suppression would break core functionality. In these modes, DONKEY
stays in Insert state (passthrough), keeping DONKEY active but
non-interfering.

*Permanently* is meant literally: there is no key that reaches Normal
state from one of these buffers. =C-g= behaves as it does in stock
Emacs — interrupting the subprocess, aborting a recursive edit — rather
than switching state, and anything that manages to turn Normal state on
by another route is bounced straight back. The modeline says
=DONKEY[E]= rather than =DONKEY[I]= there, so the difference is visible
without having to press a key to find out.

** Built-in Defaults

The following modes are excluded by default because they manage
subprocess interaction or terminal emulation where suppressing keys
via =suppress-keymap= would break functionality:

| Mode          | Reason                                                                 |
|---------------+------------------------------------------------------------------------|
| =comint-mode= | Process interaction — all input goes to subprocess. Covers derivatives |
|               | like =shell-mode=, =inferior-python-mode=, =ielm-mode=, =gud-mode=     |
|               | via =derived-mode-p=.                                                  |
| =term-mode=   | Full PTY terminal emulation — character-at-a-time, raw mode.           |
| =vterm-mode=  | Same as =term-mode= but faster implementation.                         |
| =eshell-mode= | Own command-line parser and input loop.                                |

Derived modes are caught automatically by the =derived-mode-p= check
in =donkey--excluded-mode-p= (used consistently everywhere DONKEY needs
to know whether a buffer is excluded), so listing =comint-mode= alone
covers dozens of comint derivatives.

** Adding Additional Excluded Modes

Modes like =dired-mode=, =ibuffer-mode=, =magit-status-mode=, and
=epa-key-list-mode= are NOT excluded by default. In these modes, DONKEY
Normal state works (keys are suppressed, =hjkl= navigates), but some
users may prefer passthrough to retain native keybindings.

To add modes to the exclusion list in your =config.el=:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    (dolist (mode '(dired-mode ibuffer-mode magit-status-mode epa-key-list-mode))
      (add-to-list 'donkey-excluded-modes mode)))

#+end_src

Or add a single mode:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    (add-to-list 'donkey-excluded-modes 'pdf-view-mode))

#+end_src

Verify the current exclusion list:

#+begin_src emacs-lisp

  M-x eval-expression RET donkey-excluded-modes RET

#+end_src

* Customizing Keybindings

You can override existing bindings or add new ones in your =config.el=
by modifying =donkey-normal-mode-map=.

** Override an existing binding:

#+begin_src emacs-lisp

  ;; Replace the default behavior of ';' with consult-outline
  (when (boundp 'donkey-normal-mode-map)
    (keymap-set donkey-normal-mode-map ";" #'consult-outline))

#+end_src

** Unbind a suppressed key to fall through:

#+begin_src emacs-lisp

  ;; Make ',' fall through to the major mode instead of being ignored
  (when (boundp 'donkey-normal-mode-map)
    (keymap-unset donkey-normal-mode-map ","))

#+end_src

** Add a leader key map:

#+begin_src emacs-lisp

  ;; Leader Map Definition
  (when (boundp 'donkey-normal-mode-map)
    (unless (boundp 'donkey-leader-map)
      (defvar donkey-leader-map (make-sparse-keymap)
        "Leader key map under SPC."))
    (keymap-set donkey-normal-mode-map "SPC" 'donkey-leader-map))

#+end_src

* Enter Key Rules (DWIM)

DONKEY's =donkey-enter-dwim= command dispatches the Enter (RET) key based
on context. In editing modes, Enter is blocked to prevent accidental
line breaks. In non-editing modes, the native RET binding is invoked.

For =org-mode= and =markdown-mode=, DONKEY uses a rule-based dispatch
system to execute context-aware actions when Enter is pressed.

** Which Modes Block Enter

=donkey-editing-modes= (a Customization Group variable) lists the major
modes where Enter does nothing: =prog-mode=, =text-mode=, =org-mode=,
=fundamental-mode=, =conf-mode=, =markdown-mode=, and =gfm-mode=, by
default. Derived modes are caught automatically via =derived-mode-p=,
so =prog-mode= alone covers =python-mode=, =emacs-lisp-mode=, and every
other language mode derived from it.

Any major mode NOT in this list falls through to whatever RET was
originally bound to before Normal state's keymap took over -- e.g.
=dired-find-file= in =dired-mode=, or =magit-status='s own RET binding.

To also block Enter in an additional mode, or remove one so it falls
through to its native binding, from your =config.el=:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    (add-to-list 'donkey-editing-modes 'lisp-interaction-mode)
    (setq donkey-editing-modes (delq 'conf-mode donkey-editing-modes)))

#+end_src

** Built-in Default Rules

The following rules are installed by default (controlled by
=donkey-default-enter-rules-enabled=, which defaults to =t=):

#+begin_src emacs-lisp

  ;; Toggle checkboxes in org list items
  (donkey-add-enter-rule item :checkbox org-toggle-checkbox)

  ;; Toggle TODO/DONE on org headlines
  (donkey-add-enter-rule headline :todo-type donkey-org-todo)

  ;; Follow links in org, markdown, or plain text
  (donkey-add-enter-rule link nil org-open-at-point
                       markdown-follow-thing-at-point
                       browse-url-at-point)

#+end_src

Each rule specifies:
- =ELEMENT-TYPE= :: Org element type to match (e.g. =item=, =headline=, =link=)
- =PROPERTY= :: Org element property to check (e.g. =:checkbox=, =:todo-type=), or =nil= for no property check
- =COMMANDS= :: One or more commands tried in sequence (fallback chain). The first =fboundp= and =commandp= match wins.

** Rule Priority

Rules use =add-to-list= which prepends to the front of the list. The
first matching rule wins.

To prioritize a specific command for an element type, add it LAST in
your =config.el= so it appears at the front of the dispatch list:

#+begin_src emacs-lisp

  ;; These will be checked in this order:
  ;; 1. shr-follow-link-at-point (added last, checked first)
  ;; 2. org-open-at-point (added first, checked second)
  (donkey-add-enter-rule link nil org-open-at-point)
  (donkey-add-enter-rule link nil shr-follow-link-at-point)

#+end_src

To replace a default rule entirely, disable the built-ins first, then
add your own:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    (setq donkey-default-enter-rules-enabled nil)
    (donkey-add-enter-rule link nil shr-follow-link-at-point))

#+end_src

** Disabling Built-in Rules

To define your own rules entirely, disable the defaults:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    (setq donkey-default-enter-rules-enabled nil))

#+end_src

** Adding Custom Enter Rules

Rules can be added from =config.el= using the =donkey-add-enter-rule=
macro. Example:

#+begin_src emacs-lisp

  (with-eval-after-load 'donkey
    ;; Follow links with shr-follow-link-at-point as first choice
    (donkey-add-enter-rule link nil shr-follow-link-at-point
                         org-open-at-point
                         browse-url-at-point)

    ;; Open agenda files from org-agenda table view
    (donkey-add-enter-rule org-agenda-heading nil
                         org-agenda-do-default-action))

#+end_src

** Dispatch Order

=donkey-enter-dwim= checks elements in this order:

1. =org-agenda-mode= RET binding (if in agenda)
2. Context element (most specific, e.g. a link inside a headline)
3. Parent element (e.g. the headline itself)
4. Ancestor elements (walking up the org element tree)
5. Non-editing mode native RET binding

All rules are checked at each level before moving to the next. This
ensures the most specific match fires first.

* Clipboard Integration

DONKEY's =donkey-yank= command integrates with the system clipboard,
falling back to the kill ring when no clipboard tools are available.
=donkey-yank-rectangle= does not: a rectangle has no shape a flat
clipboard could carry, so it round-trips inside Emacs only.

** Detection

DONKEY checks for clipboard tool availability fresh each time it's
needed (not cached), since the answer can differ per frame — a single
=emacs --daemon= process can have both a GUI frame (=emacsclient -c=)
and a terminal frame (=emacsclient -t=) at once, each with different
capabilities. Detection covers:
- =wl-copy= / =wl-paste= (Wayland)
- =xclip= / =xsel= (X11)
- =pbcopy= / =pbpaste= (macOS)
- Native GUI clipboard (graphical Emacs)
- Windows native clipboard

If no tools are found and Emacs is running in terminal mode, a warning
is shown once at load time. Yank operations fall back to the kill ring
silently after the first warning.

** Daemon with Mixed GUI and Terminal Frames (Wayland)

One known trap sits outside DONKEY's reach. On a pgtk Emacs daemon
serving both a GUI frame and an =emacsclient -t= frame, copy in the
GUI frame and then =donkey-yank= (=p=) in the terminal frame: the
terminal frame reads the clipboard through =wl-paste=, which asks the
compositor, which asks the owner of the selection — the very Emacs
that is now blocked waiting for =wl-paste=. The result is a hang until
the subprocess times out. Nothing in DONKEY can prevent it, because
the wait happens inside =gui-backend-get-selection= before DONKEY's
fallbacks run.

What works for us on pgtk with Emacs 31 is to route the terminal
frame's clipboard reads through a live GUI frame — pgtk serves Emacs'
own selection locally, so the round-trip through the compositor never
happens — and to have =xclip= drive =wl-copy= for writes:

#+begin_src emacs-lisp
  (use-package xclip
    :ensure t
    :init
    (setq xclip-method 'wl-copy          ; Wayland only; X11 keeps the default
          xclip-program "wl-copy")
    :config
    (xclip-mode 1))

  ;; Daemon with mixed GUI/tty frames: read the clipboard through a live
  ;; GUI frame.  pgtk serves Emacs' own selection locally, avoiding the
  ;; wl-paste self-deadlock right after a copy in a GUI frame.
  (cl-defmethod gui-backend-get-selection :around (type data-type
                                                        &context (window-system nil))
    (let ((gui-frame (seq-find #'display-graphic-p (frame-list))))
      (if gui-frame
          (with-selected-frame gui-frame
            (gui-backend-get-selection type data-type))
        (cl-call-next-method))))
#+end_src

This overrides an internal generic and is a workaround, not a
recommendation: apply it only if you see the hang described above,
and drop it once a stock Emacs no longer needs it.

* Input Method Management

DONKEY automatically saves and restores the active input method when
transitioning between Normal and Insert states. This is useful for
non-English keyboard layouts (e.g. Swedish Postfix).

- Entering Normal state: saves and deactivates the current input method
- Entering Insert state: restores the previously saved input method

This prevents input method key sequences from interfering with Normal
mode keybindings.

* Smartparens Integration

DONKEY always, with no configuration needed:
- Clears transient smartparens overlays on Insert-to-Normal transition
- Defers overlay cleanup via idle timer to avoid race conditions

Call =(donkey-setup-smartparens)= in your config after loading
=smartparens= to additionally bind =C-g= in =smartparens-mode-map= and
its overlay keymaps. This binding is opt-in and not installed
automatically. If smartparens is not installed, DONKEY functions
normally without errors.

These bindings live in Smartparens' own keymaps, independent of
=donkey-mode='s lifecycle, so they are not undone when =donkey-mode=
is disabled. That's safe: with =donkey-mode= off, pressing =C-g=
through one of these bindings falls through to =keyboard-quit=
instead of re-enabling DONKEY's Normal state.

#+begin_src emacs-lisp

  (with-eval-after-load 'smartparens
    (donkey-setup-smartparens))

#+end_src

Or with =use-package=, in =smartparens='s =:config= block, which runs
at the same point as =with-eval-after-load=:

#+begin_src emacs-lisp

  (use-package smartparens
    :ensure t
    :config
    (donkey-setup-smartparens))

#+end_src

** Wrapping a Selection with a Delimiter

Select a region (=v=/=V=), then press one of =(=, =[=, ={=, ="=, ='=,
=`= while still in Normal state to wrap it — e.g. selecting =word=
and pressing =(= yields =(word)=. This works without leaving Normal
state stuck in Insert afterward.

The actual wrapping is done by whichever pairing package you use, not
by DONKEY itself. Emacs's built-in =electric-pair-mode= needs no
third-party package:

#+begin_src emacs-lisp

  (electric-pair-mode 1)

#+end_src

It does not cover all six, though. It wraps what its own rules call a
pair — =(=, =[=, ={= and ="= — and leaves ='= and =`= alone, inserting
the character at the selection's start with the selection unwrapped:

| Pressed on a selected =alpha= | With =electric-pair-mode= |
|-------------------------------+---------------------------|
| =(=                           | =(alpha)=                 |
| =[=                           | =[alpha]=                 |
| ={=                           | ={alpha}=                 |
| ="=                           | ="alpha"=                 |
| ='=                           | ='alpha= — not wrapped    |
| =`=                           | =`alpha= — not wrapped    |

This is not the major mode's syntax table deciding: =fundamental-mode=,
=text-mode= and =emacs-lisp-mode= behave alike, though ='= has word,
punctuation and expression-prefix syntax across the three. Adding the
pair to =electric-pair-pairs= is what changes it.

Smartparens wraps all six out of the box, ='= and =`= included — it
covers more than =electric-pair-mode= here. The pair definition is what
decides, so excluding one stops that delimiter wrapping:

#+begin_src emacs-lisp

  ;; Now ' inserts rather than wraps, the same as under electric-pair-mode
  (sp-local-pair 'text-mode "'" nil :actions nil)

#+end_src

Same outcome from opposite directions: =electric-pair-mode= never knew
about the pair, Smartparens was told to leave it alone. Neither is
DONKEY doing anything different — it self-inserts with the selection
live and the pairing package decides the rest.

With *no* pairing package enabled, every delimiter is simply inserted
at point rather than wrapping the selection.

Under the hood, =donkey-normal-mode-map= normally suppresses every
printable key so it can't accidentally self-insert. These delimiters
are the one exception, and only while a region is active:
`donkey-wrap-region` momentarily enters Insert state *without*
clearing the selection first (unlike =i=/=a= and the other Insert
Mode Entry commands), runs the ordinary character insertion so that
region-wrap logic can see the still-active region, then returns to
Normal state automatically. With no region active, the key does
nothing, same as any other suppressed key in Normal state.

Under =rectangle-mark-mode= (=m v=) the behavior is different, and needs
no pairing package at all: each line of the rectangle is wrapped at
its own start and end column, with the matching close character
inserted automatically. Selecting a 3-column rectangle across three
lines of =alpha=/=bravo=/=charlie= and pressing =[= gives:

#+begin_example

  [alp]ha
  [bra]vo
  [cha]rlie

#+end_example

Bracket-type delimiters close with their real counterpart (=(= with
=)=, =[= with =]=, looked up in =donkey-mark-pair-delimiters=);
symmetric ones like ="= close with themselves. Lines shorter than the
rectangle are padded with spaces first, the same way =string-rectangle=
and other built-in rectangle commands handle them.

The delimiter set is =donkey-wrap-delimiters= (a Customization Group
variable); change it before =donkey.el= loads to add or remove
characters.

* Position Tracking

=M-x donkey-jump-back= (bound to =S=) rotates through a ring of
previously recorded cursor positions in the current buffer. Positions
are tracked automatically via =post-command-hook= whenever the cursor
moves.

It exists mainly to *undo navigation mistakes*. A big jump is easy to
mis-key — =g e= when you meant =g l= — and =S= makes that a single
keystroke to put right. Other uses suggest themselves, but it is a
recovery key rather than a filing system, and it is not a substitute for
Emacs' own bookmarks: positions are recorded as you move, so nothing in
the ring is a place you *chose* to remember.

- Ring size controlled by =donkey-position-ring-max= (default: 10)
- Ring is buffer-local — each buffer keeps its own history
- Independent of the mark ring and region
- In a narrowed buffer, only positions inside the visible portion are
  offered; if none of them are, =S= says so rather than jumping to the
  narrowing edge

To keep more (or fewer) positions, set =donkey-position-ring-max= in
your =init.el= or =config.el=, e.g. after the =load= call from
Installation:

#+begin_src emacs-lisp

  (setq donkey-position-ring-max 20)

#+end_src

Unlike =donkey-wrap-delimiters=, this takes effect immediately —
`donkey--track-position` reads it fresh on every call, so it can be
changed at any time, not just before =donkey.el= loads.

* Tutor

=g ?= (or =M-x donkey-tutor=) opens a learn-by-doing buffer, the way =C-h t= and
vimtutor do: the text holding the instructions is the text you practice
on, and changing it is the point. Lines beginning with =>>= are things to
do; everything else is explanation.

Eight lessons, ending with the two things that are DONKEY's own —
banking, and counts that mean the same thing everywhere:

1. Moving around (including =S= for undoing a mis-keyed jump)
2. Counts
3. Typing
4. Deleting and changing
5. Selecting things (words, sentences, delimiters, levels)
6. Whole lines
7. Banking
8. Copy and paste

The keys it names are *your* keys: the lessons are written with
=substitute-command-keys= escapes, so anyone who has rebound something is
taught the binding they actually have rather than the default.

Running =M-x donkey-tutor= again returns you to the buffer as you left
it. Kill the buffer to start over — nothing is written to disk.

* Troubleshooting

** A =C-g= in Insert state that sometimes does nothing

The symptom: you press =C-g= to leave Insert state and nothing happens
— or =Quit= flashes in the echo area — and the second or third press
works. Intermittently, more on some files than others, more when the
window is large.

This is not a DONKEY binding misfiring, and no package can intercept
it, because the press never becomes a keypress at all. =C-g= is also
Emacs's *interrupt character*: when it arrives while Emacs is running
Lisp, it is consumed interrupting that work — below every keymap and
every hook. And the moment right after an edit is exactly when Emacs
tends to be running Lisp: refontifying the visible window (built-in,
every configuration has this), re-spellchecking it (=jinx=), running
checkers (=flymake=, =eglot=). Press =C-g= fast after =o= or a burst
of typing — modal muscle memory does — and the press can land inside
that window and vanish. The bigger the visible region and the more
post-edit machinery, the wider the window: large frames, prose-heavy
buffers, multiple dictionaries, and many frames sharing one Emacs
(daemon setups) all raise the odds.

The confirming test: reproduce it, then immediately =C-h l=
(=view-lossage=). A press that was eaten as an interrupt is simply
absent from the key log — you pressed three times, the log shows one.

What helps is shrinking the busy window:

#+begin_src emacs-lisp
  ;; Redisplay skips fontification while input is pending, so a fast
  ;; keypress is read as a key instead of interrupting jit-lock.
  (setq redisplay-skip-fontification-on-input t)

  ;; If you run jinx: move its visible-region recheck out from under
  ;; your fingers (default is 0.2, squarely where a quick C-g lands).
  (setq jinx-delay 0.8)
#+end_src

The same idea applies to any checker with an idle delay: raise it past
your reaction time.

DONKEY also recovers on its own where recovery is possible: a quit
that unwinds to the command loop while Insert state is on is given
the meaning the press had — the exit runs instead of =Quit= being
printed. That catches the flavor you would otherwise see as a bare
=Quit= while stuck in Insert. It cannot catch a quit that redisplay
or a timer swallows before the command loop sees it — those never
reach Lisp that DONKEY controls — which is what the settings above
are for: they shrink the window in which the press can be eaten at
all. Prevention where prevention is possible, recovery where only
recovery is; together they collapse the frequency to rare.

* Development

** Running the checks locally

CI runs on every push to =master= and on every pull request (see
=.github/workflows/ci.yml=). The same four checks can be run by hand:

#+begin_src sh

  # Full ERT suite
  emacs -Q --batch -L . -L donkey-testing \
        $(for f in donkey-testing/*-test.el; do printf ' -l %s' "$f"; done) \
        -f ert-run-tests-batch-and-exit

  # Byte-compile the package, warnings treated as errors
  emacs -Q --batch --eval '(setq byte-compile-error-on-warn t)' \
        -f batch-byte-compile donkey.el

  # Documentation conventions
  emacs -Q --batch --eval "(progn (require 'checkdoc) (checkdoc-file \"donkey.el\"))"

  # MELPA packaging conventions (requires package-lint from MELPA)
  emacs -Q --batch --eval "(package-initialize)" \
        -l package-lint -f package-lint-batch-and-exit donkey.el

#+end_src

*Delete =donkey.elc= before running the test suite.* With a compiled
file present, =-L .= loads it in preference to the source, and byte-code
open-codes =delete-region=, =forward-char= and =forward-line= — which
defeats the =cl-letf= mocks several tests use to assert those were
called. Seven tests fail for reasons unrelated to any real change. CI
avoids this by keeping compilation in a separate job from the tests.

The test files themselves are deliberately not byte-compiled under
=byte-compile-error-on-warn=: they carry unused lambda arguments (mock
signatures that have to match the real command) and references to
optional third-party symbols such as =smartparens-mode-map=.

** Emacs versions

The suite runs against four versions that must all pass:

| Version             | What it is                                         |
|---------------------+----------------------------------------------------|
| =29.1=              | the minimum declared in =Package-Requires=         |
| =30.1=              | the previous stable series                         |
| =31.1=              | the current stable release                         |
| =release-snapshot=  | the release branch upstream, i.e. the next release |

=release-snapshot= is whatever branch Emacs is preparing its next
release from. At time of writing that is =emacs-31=, reporting
=31.1.50= on the way to 31.2; when upstream cuts =emacs-32= it follows
that branch without any change here, which is how 31 was covered before
it shipped. Once a release comes out of it, the released version is
pinned in the table like the others.

A fifth, =snapshot=, builds Emacs master — the next release in
development, a version nobody is running yet (it reports =32.0.50=). It
is allowed to fail without blocking the repository, so churn upstream
does not turn the build red.

The single-version jobs — each test file in isolation, Smartparens,
shuffled order, the terminal frame and lint — run on =31.1=. They test
properties of the suite rather than of Emacs; the matrix above covers
the older versions.
